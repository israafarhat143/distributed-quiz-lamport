1. INTRODUCTION GÉNÉRALE
================================================================================

Ce rapport présente le développement et l'implémentation d'un système de quiz 
distribué basé sur une architecture client-serveur, avec une intégration 
complète des mécanismes de synchronisation des systèmes distribués. Le projet 
démontre l'application pratique de concepts fondamentaux en informatique 
distribuée, notamment l'horloge de Lamport et la gestion des sections critiques.

Le système a été développé en Java, un langage idéal pour les applications 
distribuées grâce à sa portabilité et ses mécanismes de threading natifs. 
L'application combine:

• Une architecture cliente-serveur robuste
• Un mécanisme de synchronisation basé sur les horloges logiques
• Une gestion sophistiquée de la section critique
• Une interface graphique professionnelle utilisant Swing
• Un protocole de communication fiable sur TCP/IP

2. CONTEXTE ET OBJECTIFS DU PROJET
================================================================================

2.1 CONTEXTE GLOBAL

Les systèmes distribués modernes nécessitent une synchronisation précise des 
événements dans un environnement où les communications réseau introduisent des 
délais imprévisibles. Contrairement aux systèmes centralisés disposant d'une 
horloge globale commune, les systèmes distribués doivent établir un ordre 
causal des événements sans dépendre d'une synchronisation physique.

Le projet "Quiz Distribué" utilise ce contexte comme cas d'étude pratique pour:
- Démontrer l'importance de la synchronisation dans les systèmes distribués
- Implémenter et valider les théories de Lamport
- Créer une application réelle et fonctionnelle

2.2 OBJECTIFS SPÉCIFIQUES

L'implémentation devait atteindre les objectifs suivants:

✓ Connecter 3 clients simultanément à un serveur central
✓ Garantir que tous les clients doivent se connecter avant le démarrage du quiz
✓ Implémenter une horloge logique de Lamport pour tracer les événements
✓ Gérer les accès à la section critique de manière distribuée
✓ Calculer les scores en tenant compte des timestamps de Lamport
✓ Afficher un classement final synchronisé
✓ Créer une interface utilisateur intuitive et professionnelle
✓ Documenter intégralement le système

2.3 DÉLIVRABLES

Les principaux délivrables du projet incluent:

1. Code source complet (Java) avec synchronisation distribuée

3.2 COMPOSANTS PRINCIPAUX

A) COMPOSANT SERVEUR (Serveur.java)
────────────────────────────────────

Le serveur est l'entité centrale responsable de:

• La gestion des connexions entrantes (max 3 clients)
• La synchronisation du démarrage du quiz
• La distribution des questions à tous les clients
• Le calcul des scores basé sur les timestamps
• L'affichage du classement final
• La gestion de l'horloge logique globale

Le serveur maintient plusieurs structures de données importantes:
- Une liste synchronisée des clients connectés
- Une HashMap pour stocker les scores
- Une HashMap pour tracer l'état des clients
- Une horloge de Lamport partagée

B) COMPOSANTS CLIENT (Client.java, ClientThread.java)
──────────────────────────────────────────────────────

Chaque client est une entité autonome qui:

• Se connecte au serveur sur le port 12345
• Fournit un pseudo d'identification
• Attends la synchronisation avec les autres clients
• Reçoit les questions et les options
• Envoie les réponses avec timestamp de Lamport
• Affiche les résultats finaux

C) HORLOGE DE LAMPORT (LamportClock.java)
──────────────────────────────────────────

Une classe utilitaire qui maintient une horloge logique permettant:

• De tracer les événements de manière causale
• D'établir un ordre d'occurrence des événements
• De faciliter le débogage et la vérification

D) GESTIONNAIRE DE SECTION CRITIQUE (CriticalSectionManager.java)
──────────────────────────────────────────────────────────────────

Une classe qui implémente un mécanisme de synchronisation distribuée pour:

• Contrôler l'accès exclusif aux ressources partagées
• Utiliser les timestamps de Lamport pour établir la priorité
• Respecter l'ordre causal des demandes

E) INTERFACE UTILISATEUR (QuizClientGUI2.java)
───────────────────────────────────────────────

Une interface graphique Swing qui fournit:

• Un écran d'accueil invitant
• Un formulaire pour entrer le pseudo
• Un affichage clair des questions
• Des boutons cliquables pour les réponses
• Un historique des événements du quiz
• Un affichage des résultats finaux

3.3 FLUX DE COMMUNICATION

Le flux général d'exécution suit ce schéma:

1. PHASE D'ATTENTE
   ├─ Serveur: Écoute sur le port 12345
   ├─ Clients: Se connectent un par un
   └─ Serveur: Attend les 3 connexions

2. PHASE DE SYNCHRONISATION
   ├─ Chaque client: Envoie son pseudo
   ├─ Serveur: Initialise l'horloge de Lamport
   ├─ Serveur: Attends que tous les clients signalent "prêt"
   └─ Serveur: Lance le quiz pour tous

3. PHASE DE QUIZ
   ├─ Serveur: Envoie la question (avec timestamp)
   ├─ Serveur: Envoie les 4 options
   ├─ Clients: Affichent la question et les options
   ├─ Clients: Attendent la réponse du joueur
   ├─ Clients: Envoient la réponse avec timestamp local
   ├─ Serveur: Met à jour l'horloge avec le timestamp du client
   ├─ Serveur: Calcule les points (base + bonus rapidité)
   ├─ Serveur: Affiche le feedback
   └─ Répétition pour 5 questions

4. PHASE FINALE
   ├─ Tous les clients: Terminent le quiz
   ├─ Serveur: Attend confirmation de tous
   ├─ Serveur: Calcule le classement
   ├─ Serveur: Envoie les résultats à tous les clients
   └─ Clients: Affichent le classement avec message personnalisé

4. HORLOGE DE LAMPORT - THÉORIE ET IMPLÉMENTATION
================================================================================

4.1 THÉORIE FONDAMENTALE

L'horloge de Lamport est un mécanisme fondamental en informatique distribuée 
pour établir une relation d'ordre causal entre les événements dans un système 
distribué. Leslie Lamport a introduit ce concept en 1978.

DÉFINITION FORMELLE:

Une horloge logique L est une fonction qui associe à chaque événement e un 
entier L(e) tel que:

Pour tous événements a et b:
  Si a → b (a précède causalement b), alors L(a) < L(b)

En notation mathématique:
  a ≺ b ⟹ L(a) < L(b)

PROPRIÉTÉS ESSENTIELLES:

1. PROPRIÉTÉ DE CAUSALITÉ
   ──────────────────────
   Si un événement a causalement affecte un événement b (a ≺ b), 
   alors le timestamp de a est strictement inférieur au timestamp de b.

2. PROPRIÉTÉ DE MONOTONIE
   ──────────────────────
   Les timestamps augmentent toujours ou restent constants lors des 
   événements locaux successifs.

3. PROPRIÉTÉ DE COHÉRENCE
   ─────────────────────
   Deux événements causalement indépendants peuvent avoir n'importe quel 
   ordre relatif de timestamps.

4.2 ALGORITHME DE LAMPORT

L'algorithme fonctionne selon les règles suivantes:

RÈGLE 1 - ÉVÉNEMENT LOCAL:
────────────────────────
Quand un processus exécute un événement local e:
  LC_i := LC_i + 1
  L(e) := LC_i

Où LC_i est l'horloge logique du processus i.

RÈGLE 2 - ÉVÉNEMENT D'ENVOI:
───────────────────────────
Quand un processus i envoie un message m à un processus j:
  a) Incrémenter l'horloge locale
  b) Inclure L(i) dans le message m

RÈGLE 3 - ÉVÉNEMENT DE RÉCEPTION:
─────────────────────────────────
Quand un processus j reçoit un message m du processus i contenant le 
timestamp t:
  a) LC_j := max(LC_j, t)
  b) LC_j := LC_j + 1
  c) L(e) := LC_j

4.3 IMPLÉMENTATION DANS LE PROJET

Dans notre système, l'horloge de Lamport a été implémentée avec une 
considération spéciale: l'utilisation de AtomicInteger pour garantir la 
thread-safety sans locks explicites.

ARCHITECTURE DE L'IMPLÉMENTATION:

┌─────────────────────────────────────┐
│   LamportClock.java                 │
├─────────────────────────────────────┤
│ - AtomicInteger time                │
│ - tick(): void                      │
│ - update(int received): int         │
│ - getTime(): int                    │
│ - reset(): void                     │
│ - compare(int other): int           │
└─────────────────────────────────────┘

SÉMANTIQUE DES OPÉRATIONS:

1. tick()
   ──────
   Incrémente l'horloge pour un événement local.
   
   Utilisation dans le projet:
   • Serveur: Avant d'envoyer une question
   • Serveur: Avant de diffuser les résultats finaux
   • Clients: Avant d'envoyer une réponse
   
   Impact: Maintient la progression monotone du temps

2. update(int received)
   ────────────────────
   Met à jour l'horloge locale avec le timestamp reçu.
   
   Formule: LC_local := max(LC_local, received) + 1
   
   Utilisation dans le projet:
   • Serveur: À la réception d'une réponse client
   • Serveur: À la réception d'un pseudo
   
   Impact: Synchronise les horloges et maintient la causalité

3. getTime()
   ─────────
   Retourne la valeur actuelle de l'horloge.
   
   Utilisation: Inclure dans les messages envoyés

4.4 GARANTIES FOURNIES

Grâce à l'implémentation de Lamport, notre système garantit:

✓ ORDRE CAUSAL: Les événements sont traçables dans leur ordre causal
✓ DÉTERMINISME: Mêmes conditions ⟹ même ordre d'événements
✓ TRAÇABILITÉ: Chaque événement a un timestamp unique
✓ DEBUGGABILITÉ: Les logs contiennent des timestamps utiles

4.5 CAS D'USAGE DANS LE PROJET

EXEMPLE 1 - ENVOI DE QUESTION
──────────────────────────────

Événements au serveur:
  1. [TS:3] tick() ⟹ LC_serveur = 4
  2. [TS:4] Envoyer "Question 1"
  3. [TS:4] Envoyer "Option 1"
  4. [TS:4] Envoyer "Option 2"
  5. [TS:4] Envoyer "Option 3"
  6. [TS:4] Envoyer "Option 4"

Événements au client:
  1. Recevoir "Question 1" avec TS=4
  2. update(4) ⟹ LC_client = max(2, 4) + 1 = 5
  3. Afficher la question
  4. Attendre réponse utilisateur

EXEMPLE 2 - RÉCEPTION DE RÉPONSE
─────────────────────────────────

Événements client:
  1. Utilisateur clique option 2
  2. tick() ⟹ LC_client = 6
  3. Envoyer "2|CLOCK|6"

Événements serveur:
  1. Recevoir "2|CLOCK|6" du client
  2. update(6) ⟹ LC_serveur = max(4, 6) + 1 = 7
  3. Calculer points basé sur (7 - 4) = 3
  4. Ajouter score: points = 10 + max(0, 10 - 3) = 17

5. GESTION DE LA SECTION CRITIQUE
================================================================================

5.1 CONCEPT FONDAMENTAL

Une SECTION CRITIQUE est une portion de code dans un système distribué où 
l'accès à une ressource partagée doit être:

• EXCLUSIF: Un seul processus à la fois
• ORDONNÉE: Respectant un ordre juste (fair ordering)
• SANS DEADLOCK: Pas de blocage perpétuel

Dans les systèmes centralisés, on utilise des verrous (locks) classiques.
Dans les systèmes distribués, des approches plus sophistiquées sont nécessaires.

5.2 ALGORITHME RICART-AGRAWALA

Notre implémentation utilise une approche inspirée par l'algorithme 
Ricart-Agrawala, qui combine:

• Les horloges de Lamport pour l'ordonnance
• Une file d'attente de priorité pour l'ordre juste
• Un mécanisme de vote/consentement distribué

ALGORITHME:

┌─────────────────────────────────────────────────────────┐
│ PHASE 1: DEMANDE D'ENTRÉE                               │
├─────────────────────────────────────────────────────────┤
│ 1. Incrémenter l'horloge logique                        │
│ 2. Créer une demande (timestamp, processus_id)          │
│ 3. Ajouter à la file d'attente locale                   │
│ 4. Envoyer la demande à tous les autres processus       │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ PHASE 2: VÉRIFICATION DE PRIORITÉ                       │
├─────────────────────────────────────────────────────────┤
│ 1. Trier les demandes par (timestamp, id)               │
│ 2. Vérifie si ma demande est première                   │
│ 3. Si non, attendre avec wait()                         │
│ 4. Si oui, procéder à l'entrée                          │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ PHASE 3: SECTION CRITIQUE                               │
├─────────────────────────────────────────────────────────┤
│ 1. Accès exclusif à la ressource                        │
│ 2. Effectuer les opérations critiques                   │
│ 3. Libérer la ressource                                 │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│ PHASE 4: LIBÉRATION                                     │
├─────────────────────────────────────────────────────────┤
│ 1. Retirer ma demande de la file                        │
│ 2. notifyAll() pour réveiller les attendeurs            │
│ 3. Les autres processus recalculent leur priorité       │
└─────────────────────────────────────────────────────────┘

5.3 IMPLÉMENTATION DANS LE PROJET

RESSOURCES CRITIQUES PROTÉGÉES:

1. ACCÈS À LA LISTE DES CLIENTS
   ──────────────────────────────
   Ressource: Collections.synchronizedList<ServeurThread>
   Protection: Locks intrinsèques de Java
   Raison: Éviter les modifications concurrentes

2. HASHMAP DES SCORES
   ──────────────────
   Ressource: HashMap<String, Integer> scores
   Protection: Méthodes synchronized
   Raison: Garantir la cohérence des mises à jour

3. COMPTEUR DE JOUEURS PRÊTS
   ─────────────────────────
   Ressource: volatile int readyCount
   Protection: Object.wait() / notifyAll()
   Raison: Synchroniser le démarrage du quiz

4. COMPTEUR DE JOUEURS TERMINÉS
   ────────────────────────────
   Ressource: volatile int finishedCount
   Protection: Object.wait() / notifyAll()
   Raison: Synchroniser l'affichage des résultats

5.4 IMPLÉMENTATION DÉTAILLÉE

EXEMPLE: PROTECTION DU CALCUL DE SCORE

┌──────────────────────────────────────────────────────────┐
│ PROBLÈME SANS PROTECTION:                                │
├──────────────────────────────────────────────────────────┤
│ Processus A: score = scores.get("Alice") = 50            │
│ Processus B: score = scores.get("Alice") = 50            │
│ Processus A: ajouter 10 points                           │
│              scores.put("Alice", 60)                     │
│ Processus B: ajouter 15 points                           │
│              scores.put("Alice", 65)   ← 10 points perdus
│                                                          │
│ Résultat: 60 au lieu de 75 ❌                             │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│ SOLUTION AVEC SECTION CRITIQUE:                          │
├──────────────────────────────────────────────────────────┤
│ synchronized void addScore(String name, int points) {    │
│     int current = scores.getOrDefault(name, 0);          │
│     scores.put(name, current + points);                  │
│ }                                                        │
│                                                          │
│ Exécution atomique: Lecture + Modification + Écriture    │
│ Résultat: 75 points ✓                                     │
└──────────────────────────────────────────────────────────┘

5.5 PRIORITÉS DANS LES SECTIONS CRITIQUES

Notre système utilise un système de priorité basé sur les timestamps:

┌───────────────────────────────────────────┐
│ COMPARATEUR DE PRIORITÉ                   │
├───────────────────────────────────────────┤
│ Priority = (timestamp, processId)         │
│                                           │
│ Exemple:                                  │
│ (4, "Alice") > (4, "Bob")   [Alice gagne] │
│ (3, "Charlie") > (5, "David")             │
│           [Charlie gagne]                 │
│                                           │
│ Formule: (ts1, id1) < (ts2, id2) si:     │
│ • ts1 < ts2, OU                           │
│ • ts1 == ts2 ET id1 < id2                 │
└───────────────────────────────────────────┘

5.6 GARANTIES DE LA SECTION CRITIQUE

Notre implémentation garantit:

✓ EXCLUSIVITÉ MUTUELLE
  Un seul processus ne peut être dans la section critique à la fois

✓ ÉQUITÉ
  Aucun processus ne peut être indéfiniment bloqué si d'autres 
  cherchent à entrer

✓ CAUSALITÉ RESPECTÉE
  Les timestamps de Lamport ordonnent les demandes causalement

✓ ABSENCE DE DEADLOCK
  Pas de situation où deux processus s'attendent mutuellement

✓ VIVACITÉ (LIVENESS)
  Si un processus veut entrer, il finira par entrer

6. MÉCANISMES DE SYNCHRONISATION DISTRIBUÉE
================================================================================

6.1 SYNCHRONISATION DU DÉMARRAGE

Le système doit garantir que le quiz ne démarre que quand les 3 clients 
sont connectés et prêts.

MÉCANISME:

┌─────────────────────────────────────────────────────────────┐
│ PHASE 1: ATTENDRE 3 CONNEXIONS                              │
├─────────────────────────────────────────────────────────────┤
│ while (playerCount < expectedPlayers) {                     │
│     Socket clientSocket = serverSocket.accept();            │
│     // Créer un thread pour ce client                       │
│     // Incrémenter playerCount                              │
│ }                                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ PHASE 2: CHAQUE CLIENT SIGNALE "PRÊT"                       │
├─────────────────────────────────────────────────────────────┤
│ synchronized void playerReady(String name) {                │
│     readyCount++;                                           │
│     scores.put(name, 0);  // Initialiser score             │
│     if (readyCount == expectedPlayers) {                    │
│         startLock.notifyAll();                              │
│     }                                                       │
│ }                                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ PHASE 3: SERVEUR ATTEND TOUS LES PRÊTS                      │
├─────────────────────────────────────────────────────────────┤
│ synchronized (startLock) {                                  │
│     while (readyCount < expectedPlayers) {                  │
│         startLock.wait();                                   │
│     }                                                       │
│ }                                                           │
└─────────────────────────────────────────────────────────────┘

GARANTIE: Le quiz ne commencera PAS avant que tous les clients soient prêts.

6.2 SYNCHRONISATION DE LA FIN DU QUIZ

De même, les résultats ne sont affichés que quand tous ont fini.

MÉCANISME:

┌─────────────────────────────────────────────────────────────┐
│ PHASE 1: CLIENT ANNONCE LA FIN                              │
├─────────────────────────────────────────────────────────────┤
│ synchronized void playerFinished(String name) {             │
│     finishedCount++;                                        │
│     if (finishedCount >= expectedPlayers) {                 │
│         endLock.notifyAll();                                │
│     }                                                       │
│ }                                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ PHASE 2: SERVEUR ATTEND TOUS LES TERMINÉS                   │
├─────────────────────────────────────────────────────────────┤
│ synchronized (endLock) {                                    │
│     while (finishedCount < expectedPlayers) {               │
│         endLock.wait(5000);  // Timeout 5s                  │
│     }                                                       │
│ }                                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ PHASE 3: AFFICHER LES RÉSULTATS                             │
├─────────────────────────────────────────────────────────────┤
│ displayFinalScores();     // Afficher sur le serveur        │
│ broadcastFinalResults();  // Envoyer aux clients            │
│ resultsDisplayed = true;                                    │
│ resultsLock.notifyAll();                                    │
└─────────────────────────────────────────────────────────────┘

6.3 MÉCANISME WAIT/NOTIFY

Java fournit un mécanisme de notification par objet pour la synchronisation:

SÉQUENCE TEMPORELLE:

┌──────────────────────────────────────────────────┐
│ THREAD CONSOMMATEUR (Serveur)                    │
├──────────────────────────────────────────────────┤
│ 1. synchronized (startLock) {                    │
│ 2.     while (readyCount < 3) {                  │
│ 3.         startLock.wait();  ← BLOQUÉ            │
│ 4.     }                                         │
│ 5. }                                             │
│ 6. // Continue avec quiz                        │
└──────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│ THREAD PRODUCTEUR (Client 1, 2, 3)               │
├──────────────────────────────────────────────────┤
│ Client 1: playerReady("Alice")                   │
│           readyCount = 1                         │
│                                                  │
│ Client 2: playerReady("Bob")                     │
│           readyCount = 2                         │
│                                                  │
│ Client 3: playerReady("Charlie")                 │
│           readyCount = 3                         │
│           startLock.notifyAll() ← RÉVEILLE       │
│                                                  │
│ Serveur: wait() retourne, continue               │
└──────────────────────────────────────────────────┘

───────────────────────────────────

Temps [ms]  | Serveur                    | Clients
────────────┼────────────────────────────┼──────────────
0           | Envoie Question            | Reçoit Q

250         | Traite B (section critique)|

VALIDATION 2: Équité (Fair Ordering)
────────────────────────────────────
Processus demandent accès (par timestamp Lamport):
  TS=4 (Alice)    ← Première entrée
  TS=4 (Bob)      ← Deuxième (même TS, mais Alice < Bob)
  TS=5 (Charlie)  ← Troisième

Ordre d'accès: Alice → Bob → Charlie
Résultat: ✓ Ordre juste respecté

9.2 DÉFIS SURMONTÉS

1. Synchronisation des timestamps entre clients et serveur
   Solution: Algorithme de Lamport avec update() approprié

   Solution: Patterns wait/notify du Java concurrent

3. Affichage des résultats atomique
   Solution: Mécanisme resultsDisplayed + waitForResults()

4. Interface graphique responsive pendant les I/O réseau
   Solution: Threads séparés pour lecture serveur

5. Validation des réponses utilisateur
   Solution: Boucles de validation avec retry
